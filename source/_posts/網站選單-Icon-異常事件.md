## 1. 事件摘要

- **事件名稱：** 澳洲使用者無法正常顯示網站選單 Icon
- **影響範圍：** 澳洲使用者
- **使用者可見症狀：** 選單文字正常，但所有選單 Icon 消失
- **相關技術：** CDN、登入 Cookie／存取規則、`.woff` 字型檔、IIS 靜態內容 MIME 設定
- **目前狀態：** 已恢復正常（依 End User 回報）
- **程式碼變更：** 本次處理未指出需要修改 Icon 相關程式碼

## 2. 問題現象

澳洲使用者回報網站選單 Icon 無法顯示，但選單文字仍正常。其他地區當時沒有回報相同問題。

由於多個 Icon 同時消失，而文字仍正常，初步將調查重點放在共用的 Icon CSS 或字型資源，而非個別選單的程式碼。

## 3. 調查與排查流程

### 3.1 初步排查瀏覽器快取

先請澳洲使用者使用 Windows 瀏覽器執行 `Ctrl + F5` 強制重新載入頁面，以排除部分瀏覽器本機快取因素。

> `Ctrl + F5` 不會清除 CDN 遠端快取，也不等同於清除瀏覽器的所有資料。

### 3.2 檢查字型資源請求

使用瀏覽器開發者工具（`F12`）查看 Network 中的 `.woff` 字型檔請求，發現請求回應為 **HTTP 302**。

另以測試用 `.woff` URI 直接測試，結果會被導向網站登入頁面。這顯示字型檔請求可能受到登入驗證或 CDN 存取規則影響，未能取得真正的字型檔案。

### 3.3 與 Infra 人員確認 CDN 規則

向相關人員確認後，得知<span style="color: red;">公司 CDN 可針對特定網域的副檔名設定存取規則，使其保留 Cookie 資訊。(相關內容參考補充8.2)</span>

將此線索提供給 Infra 人員處理後，End User 回報目前顯示已恢復正常。

## 4. 根因分析

### 最可能的原因

依照目前取得的線索，本次問題**最可能與 CDN 對 `.woff` 字型檔的 Cookie／存取規則有關**：

1. 網頁載入選單 CSS。
2. 瀏覽器請求 `.woff` 字型檔。
3. 字型檔請求未能依預期通過存取驗證，回應 HTTP 302 並導向登入頁面。
4. 瀏覽器未能取得真正的字型內容，因此所有依賴該字型的選單 Icon 無法正常顯示。
5. Infra 調整 CDN 規則後，End User 回報顯示正常。

### 根因確認程度

目前有以下支持證據：

- `.woff` 請求回應 HTTP 302。
- 直接開啟測試用 `.woff` URI 會被導向登入頁面。
- Infra 調整 CDN 規則後，End User 回報恢復正常。

因此，可將 **CDN 字型資源存取／Cookie 規則不相容**列為最可能根因。不過，若尚未保留調整後 `.woff` 請求的 HTTP 狀態碼及回應內容，則不宜宣稱已透過技術紀錄完全證實根因。

## 5. 處理結果

- Infra 人員調整 CDN 中針對特定副檔名的存取規則。
- End User 回報網站目前顯示正常。
- 目前無證據顯示需要修改 Icon 相關程式碼。
- 事件狀態：**已恢復正常，建議持續觀察。**

## 6. 後續驗證與建議

建議確認並記錄以下項目：

- [ ] 澳洲使用者確認所有選單 Icon 均正常顯示。
- [ ] 在 Network 中確認 `.woff`／`.woff2` 請求回傳成功，且回應內容為字型資料，而非登入頁面的 HTML。
- [ ] 確認調整後不再發生導向登入頁面的非預期 HTTP 302。
- [ ] 確認網站登入、權限驗證及其他受保護資源仍正常。
- [ ] 確認 CDN 規則只涵蓋可安全公開讀取的靜態字型資源，避免不慎放寬其他受保護資源的存取權限。
- [ ] 記錄 Infra 變更內容、時間及適用的副檔名／URL 範圍，以利日後追蹤。

## 7. 經驗與預防措施

1. **將公開靜態資源與登入驗證資源分開管理。** 若 Icon 字型檔不含敏感內容，可評估讓其以不依賴登入 Cookie 的方式提供，並遵循公司資安政策。
2. **針對 CSS 與字型檔建立檢查流程。** Icon 全面消失但文字正常時，優先檢查共用 CSS、`.woff`／`.woff2` 請求、HTTP 狀態碼及 `Content-Type`。
3. **避免只依賴清除快取。** `Ctrl + F5` 只能協助排除部分瀏覽器快取問題，不能清除 CDN 遠端快取，也無法修正 Cookie 或存取驗證設定。
4. **保留修正前後的證據。** 建議記錄請求 URL（遮蔽敏感資訊）、狀態碼、`Location`、`Content-Type` 及 CDN 相關回應標頭，以便未來快速定位。

## 8. 補充

1. **2026年5月份即遇過相同問題**
收到IT Mail告知，下列副檔名將進行CDN Cache機制調整：*.woff, *.woff2, *.bmp,*.css, *.jpg,*.js, *.svg, *.html....etc。調整後，出現icon消失的問題。經查，<span style="color: red;">經過CDN的檔案的HTTP Response裡的set-Cookie header會被拿掉，導致檔案無法顯示(因為不是匿名存取)，回應302。</span>

2. **CDN為什麼要把cookie資訊拿掉?**
CDN（內容傳遞網路）在快取（Cache）時會把 Cookie（尤其是 Set-Cookie）移除或過濾掉，主要是為了保護用戶隱私、避免資料錯亂以及確保快取機制的正確性。
詳細原因如下：
- 避免私人資訊外洩與共用：
Cookie 通常包含特定用戶的登入狀態、身分識別或個人偏好。CDN 的核心功能是把靜態或共用內容儲存起來，分發給成千上萬不同的使用者。如果在 Cache Hit（快取命中）時把某個特定用戶的 Set-Cookie 一起快取並送給下一個使用者，就會造成嚴重的資料外洩與帳號錯亂問題。
- 確保快取不會失效或膨脹：
每個使用者的 Cookie 值通常都不同。如果 CDN 把 Cookie 納入快取判斷依據（Vary by Cookie），每一個使用者打過來都會被視為不同的 Cache Key，導致 CDN 的快取命中率（Cache Hit Rate）大幅下降，失去加速的意義。
- 動態與靜態分流：
像登入（Login）、驗證等會產生 Set-Cookie 的行為本質上屬於動態請求。CDN 主要負責優化靜態資源，因此在處理快取回應時，會主動移除與個人化狀態相關的 Cookie 標頭。

3. **字型檔的請求回應為302(重新導頁)**
因為沒取得身分驗證訊息，所以回傳302，重新導向到登入頁面，要你重新登入。正常的話是回應代碼200

## 9. 結論

本次澳洲網站選單 Icon 異常，表現為選單文字正常、所有 Icon 消失。排查時發現 `.woff` 字型檔請求回應 HTTP 302，且測試字型 URI 會導向登入頁面。經 Infra 人員調整 CDN 特定副檔名的存取規則後，End User 回報目前顯示正常。

**結論：** 本次事件最可能與 CDN 對字型檔的 Cookie／存取規則有關。建議以調整後的 Network 請求成功紀錄作為最終驗證，並確認規則未影響其他受保護資源。
