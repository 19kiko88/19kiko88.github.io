建立OAuth Server with OpenIddict(1)

用OpenIddict建立一個測試用remote MCP Server專案

核心職責
MCP Client（Claude Desktop）: 使用者實際操作的程式；發起登入、拿到token、呼叫工具
OAuth Server（我們在做的）: 驗證身分、簽發/管理OAuth token
MCP Server（下一階段）: 實際執行MCP工具、回傳資料

跟誰說話
MCP Client（Claude Desktop）: OAuth Server（登入/換token）、MCP Server（呼叫工具）
OAuth Server（我們在做的）: MCP Client（發token）、PCBRepairNavi（確認身分）
MCP Server（下一階段）: MCP Client（收工具呼叫請求）

具體做的事

  • MCP Client（Claude Desktop）:
    1. 打開瀏覽器導向/connect/authorize
    2. 臨時開本機loopback server接Authorization Code
    3. 拿code+code_verifier換access_token/refresh_token
    4. 帶著access_token呼叫MCP Server的工具
  • OAuth Server（我們在做的）:
    1. /connect/authorize：依client_id導向Bridge，確認PNP身分，簽發Authorization Code
    2. /connect/token：驗證PKCE，換發access_token/refresh_token；refresh時做IsTokenActive+ticketExpiration雙層檢查
    3. 發布JWKS、discovery metadata
  • MCP Server :
    1. 驗證收到的access_token（用OAuth Server的JWKS驗簽、檢查exp/iss/aud/scope）
    2. 依scope決定能不能呼叫該工具
    3. 呼叫IUcsService方法，或呼叫PCBRepairNavi的Native Capability API（含per-user權限比對）
    4. 把結果回傳給MCP Client

MCP Client：使用者的代理人，負責「登入」跟「發出請求」。
OAuth Server：門禁警衛，負責「確認你是誰、給你通行證（token）」，不管你進去之後要做什麼。
MCP Server：真正做事的窗口，負責「看你的通行證夠不夠權限、幫你實際把事情辦好（呼叫UcsService等）」。

幾個關鍵點說明：

  • AllowAuthorizationCodeFlow() + AllowRefreshTokenFlow() 是刻意只開這兩個——OAuth2.1 明確拿掉 Implicit Grant 跟 Resource Owner Password Credentials Grant，我們沒有呼叫對應的 Allow…Flow()，它們就是被禁用的狀態。
  • RequireProofKeyForCodeExchange() 讓 PKCE 變成強制（不是只對 public client 選擇性開啟），符合OAuth2.1的要求。
  • DisableAccessTokenEncryption() 是設計文件第9節提到的坑——沒加這行，OpenIddict 預設會把 access token 加密，外部的 MCP Resource Server 之後用 JWKS 公鑰會驗不了簽。
  • AddDevelopmentSigningCertificate() 現在先用開發用的自簽憑證只是為了先讓程式跑得起來，正式上線前一定要換成正式保管的簽章憑證（對應設計文件第8.1節），這個我們會在後面的步驟特別處理，不會漏掉。
  • EnableAuthorizationEndpointPassthrough() / EnableTokenEndpointPassthrough() 這兩行很重要：讓 OpenIddict 不要自己把請求整個吃掉處理完，而是解析驗證完基本協定格式後，把控制權交給我們自己的 Controller action——這是後面要接 Bridge 登入橋接邏輯的關鍵，沒開這個就沒辦法插入自訂邏輯。

請注意：這步做完後，如果你現在就手動打 /connect/authorize，會出錯或404——這是正常的，因為我們還沒寫對應的 Controller action 來接手處理（下一步才會寫）。不用懷疑這步做錯了。

這組 ID 的用途是告訴 Google：「我是痞客邦註冊的登入應用程式，現在要請使用者透過 Google 帳號進行登入。」
所以，Client ID 就像是應用程式向 Google 出示的身分識別證。當你將登入請求送往 Google時，參數就要附上痞客幫的 Client ID，來讓Goole驗證伺服器辨識是哪個應用程式。

Client ID用途如下：

  1. 確認 Client 是否已註冊及可使用
    根據請求中的 client_id，查詢 OpenIddict 的應用程式註冊資料，確認該 Client 是否存在，以及是否符合伺服器的啟用狀態與使用政策。
  2. 驗證 Redirect URI
    確認請求中的 redirect_uri(驗證身分後，要導回的頁面) 是否符合該 Client 註冊時設定的允許網址，避免授權結果被導向未經允許的網站。
  3. 驗證 PKCE
    如果該 Client 必須使用 PKCE，授權請求就必須包含符合規定的 code_challenge 與 code_challenge_method。之後交換授權碼時，伺服器還必須驗證 code_verifier 是否與原本的 Challenge 相符。
  4. 限制 Scope 權限
    確認請求中的 scope 是否在該 Client 被允許要求的範圍內，避免 Client 取得超出其註冊權限的存取範圍。
  5. 限制允許的授權流程
    檢查該 Client 是否被允許使用目前要求的授權流程，例如 Authorization Code Flow，以及是否符合相應的 Response Type、Endpoint 與其他安全政策。

一句話總結：Client ID 的核心用途是「識別這次請求是以哪個已註冊的應用程式名義提出」，再由 OAuth Server 根據該 Client 的註冊設定、授權流程與安全驗證機制，決定是否接受這次請求。

  • 什麼是 .well-known/openid-configuration？

/.well-known/openid-configuration 是標準化路徑，每個 OpenID Connect 提供者都會在此公布設定。將它接在任一 OIDC issuer 的基底 URL 後面，即可取得一份 JSON，列出該提供者的端點、支援功能與密碼學能力。

例如：
Google：https://accounts.google.com/.well-known/openid-configuration
Microsoft：https://login.microsoftonline.com/{tenant}/v2.0/.well-known/openid-configuration

詳細可以參考： 什麼是 .well-known/openid-configuration？開發者指南

幾個重點說明：

  • HttpContext.GetOpenIddictServerRequest() 是OpenIddict提供的方法，因為Step 6開了EnableAuthorizationEndpointPassthrough()，這裡才能拿到OpenIddict已經先驗證過基本格式（client_id存在、redirect_uri吻合、PKCE必填等）的請求物件。
  • GenerateNonce() 用 RandomNumberGenerator（密碼學安全的亂數來源，不是Random），產生URL-safe的字串。
  • Authorize action身兼兩種情況：用resumeNonce（也就是__nonce查詢參數）是否存在來判斷「這是第一次經過還是第二次繞回來」。兩種情況都發生在同一個/connect/authorize路徑上，這是刻意的——OpenIddict只有在請求打到設定的端點路徑時，才會建立它內部需要的「交易狀態」，SignIn()只有在這個狀態存在時才能被正確攔截轉換成簽發Authorization Code的行為。如果在別的路徑（例如一個獨立的resume端點）呼叫SignIn()，OpenIddict會認不出這個請求、丟出例外。
  • BridgeCallback本身不呼叫SignIn()：它的工作只有「驗證nonce、呼叫Redeem、把身分資料寫回PendingAuthorizeRequest、再轉一手導回/connect/authorize」。真正的SignIn()留到CompleteAuthorizationAsync（在Authorize第二次經過時才呼叫），原因同上。
  • pending.Used在BridgeCallback裡先不標記true：故意的。如果標記了但後面CompleteAuthorizationAsync因為某些原因失敗，這筆暫存資料就變成「已用過但沒真的完成授權」的死資料，使用者會卡住。留到CompleteAuthorizationAsync真正成功簽完才標記，確保狀態一致。
  • QueryHelpers.AddQueryString加上.Where(p => p.Value is not null)過濾：因為scope、state這些欄位在原始請求裡可能是null，直接塞進字典組URL會產生scope=這種空值參數，容易讓OpenIddict重新解析時行為不一致，所以先過濾掉null的。
  • GenerateNonce()用RandomNumberGenerator而非Random：這個nonce是安全機制的一部分（防止有人用猜的nonce去冒用別人的Bridge結果），一定要用密碼學安全的亂數來源。
  • identity.SetClaim(Claims.Subject, pending.UserName)等claims設定：Claims.Subject對應JWT的sub，site_code/token_id/ticket_expiration是我們自訂的claim，供之後Step 7（Refresh雙層檢查）讀取用；claim.SetDestinations(Destinations.AccessToken)明確指定這些claim要寫進access token裡，不設的話OpenIddict預設可能不會把自訂claim放進去。
  • RedeemAsync目前回傳假資料：單純是因為RepairNavy那邊的/api/internal/sso/redeem還沒做，先讓你能測完這條Authorization Server自己的邏輯，不用等對方。

  3. 查PendingAuthorizeRequests表，確認UserName等欄位有被填入、最後Used變成true。

流程總結說明：

執行順序：MCP Client => Authenrize() => 302轉址到BNB的Bridge，進行登入確認流程，確定為登入後取得BridgeCode => BridgeCallback(bridgeCode, nonce) & RedeemAsync()取得BNB的身分驗證資料 => Authorize() => CompleteAuthorizationAsync()

  1. MCP Client 發起請求（透過瀏覽器）→ 打到 Authorize()。
  2. 因為沒帶__nonce（第一次經過），Authorize()存PendingAuthorizeRequest，回302 → 瀏覽器被導去BNB的Bridge（/sso/bridge，還沒做），BNB驗證完產生BridgeCode，再302導回我們的bridge-callback。
  3. 瀏覽器打到 BridgeCallback(code, nonce)，裡面呼叫 RedeemAsync()（目前假資料）換到{userName, siteCode, tokenId, ticketExpiration}，寫回PendingAuthorizeRequest，再302導回/connect/authorize（帶__nonce）。
  4. 瀏覽器再次打到 Authorize()（第二次經過，這次帶著__nonce）。
  5. 因為帶了__nonce，呼叫 CompleteAuthorizationAsync()：查出身分資料、組ClaimsPrincipal、SignIn()簽發Authorization Code，302導回MCP Client真正的redirect_uri，流程結束。
完成上述流程表示身分確認完成，驗證伺服器從登入單位(BNB)確認真的有這個人，並從BNB取得了登入者資訊（userName/siteCode/tokenId/ticketExpiration），Authorization Server依此簽發了Authorization Code，但還沒有取得Access Token，我們必須要用Authorization Code這個憑證，再去兌換Access Token。

Authorization Code：[身分 + 授權範圍]認證完成的依據
Acess Token：是否有呼叫API權限的依據

11：實作/connect/token端點，處理authorization_code grant

這一步在做什麼：讓MCP Client可以拿Authorization Code（加上code_verifier）真正換到access_token/refresh_token。目前先只處理authorization_code這個grant type，refresh_token那個（含IsTokenActive+ticketExpiration雙層檢查，設計文件Step 7）留到下一步，避免一次塞太多邏輯。

在AuthorizationController.cs裡加一個新的action：

幾個重點說明：

  • request.IsAuthorizationCodeGrantType()：OpenIddict提供的擴充方法，檢查這次請求的grant_type參數是不是authorization_code。
  • HttpContext.AuthenticateAsync(OpenIddictServerAspNetCoreDefaults.AuthenticationScheme)：這一行不是重新驗證什麼，是把OpenIddict內部已經跟這個Authorization Code綁在一起的那個ClaimsPrincipal（也就是我們在CompleteAuthorizationAsync()裡組出來、拿去SignIn()的那個）取回來。
  • 這裡再呼叫一次SignIn()，是在**/connect/token這個請求**裡呼叫（不是/connect/authorize），OpenIddict的token endpoint passthrough機制會把這次呼叫轉換成「簽發access_token跟refresh_token、回傳JSON給呼叫端」的行為。

  1. Method選POST，網址https://localhost:7280/connect/token。
  2. Body類型選Form URL Encoded（不是JSON）。
  3. 填入欄位：
    • grant_type = authorization_code
    • code = 剛剛從302回應的redirect_uri裡拿到的那個code值
    • redirect_uri = https://localhost:5055/callback（要跟當初/connect/authorize那次送的完全一樣）
    • client_id = pnp-mcp-client
    • code_verifier = 你最早用PowerShell算出來的那個code_verifier原始值（不是code_challenge）

請執行後確認：

  2. 送出後預期拿到200回應，body是JSON，裡面有access_token、refresh_token、token_type、expires_in這些欄位。
  3. 把拿到的access_token複製起來（之後有機會可以貼到jwt.io這類工具解開看裡面的claims，確認sub是不是test\mockuser）。
